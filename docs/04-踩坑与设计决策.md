# 踩坑与设计决策

> 这份文档记录**所有"看起来能用、实际会坏"的地方**。每条都有现场证据和最终结论，
> 照着做可以省掉大量试错时间。

---

## 1. SCCB 在"出流瞬间"开始 NACK（最费时的一个）

### 现象

相机初始化日志成片刷错：

```
E sccb-ng: SCCB_Write Failed addr:0x30, reg:0xff, data:0x01, ret:259
```

`259 = ESP_ERR_INVALID_STATE` —— IDF 新 I2C 驱动在从机 NACK 后会把总线标记为无效，后续调用连锁失败。
更麻烦的是**它不总是失败**：能出图，但帧率只有 4.9 fps。

### 定位（逻辑分析仪 + 自写解码器）

抓了两块摄像头模块的波形，用 Python 解出 SCCB 事务：

| 采集 | PCLK 启动 | 首个 NACK | 差值 |
|---|---|---|---|
| 模块 A | 84.8 ms | 85.5 ms | +0.7 ms |
| 模块 B | 217.1 ms | 217.2 ms | +0.1 ms |

按"出流前/后"切分：

| 阶段 | 模块 A | 模块 B |
|---|---|---|
| 出流前 | 11 成功 / **0 失败** | 11 成功 / **0 失败** |
| 出流后 | 153 成功 / **53 失败** | 250 成功 / **23 失败** |

**结论**：传感器一开始输出 PCLK/D0-D7，并行数据线就在干扰 SDA/SCL。24P FPC 上这些线全程平行，100 kHz 的时序裕量不够。换模块只是把 26% 降到 8%，现象不变。

> 顺带：帧率只有 4.9 fps 是因为 SCCB 没写进去 → 传感器停在上电默认 UXGA 分辨率，
> DMA 只按 96×96 截断了大图的一角。**"能出图"不等于"配置生效"**。

### 修复（以及一个被推翻的猜想）

最初的对策是"把 SCCB 降到 10 kHz"。**这个方案实际上从未生效**：

```c
// components/esp32-camera/Kconfig
config SCCB_CLK_FREQ
    int "SCCB clk frequency"
    default 100000
    range 100000 400000        // ← 下限就是 100 kHz
```

无论把 `CONFIG_SCCB_CLK_FREQ` 改成多少，**只要低于 100000，下一次构建就会被 Kconfig 静默改回去**。
（我们曾经 sed 成 10000、编译通过、也以为生效了，直到某次核对 `build/config/sdkconfig.h` 才发现一直是 100000。）

**真正让问题消失的是删掉一段调试代码**：我们曾在初始化之后再调一次
`set_pixformat / set_framesize` 去"验证通路"——但那时传感器**已经在出流**，
这次写寄存器正好撞上干扰窗口，白送一批 NACK。删掉它，初始化写入全部发生在出流之前，就不再失败。

同时换用信号完整性更好的相机模块（同样 100 kHz 下，NACK 从 53/206 降到 23/273）。

### 结论与建议

- **默认保持在 100 kHz**，不要试图降到 10 kHz（Kconfig 不允许）
- **初始化完成后不要再写传感器寄存器**——这是本问题的真正根因
- 运行期**绝不要**切分辨率/格式（`esp_camera_reconfigure` 会重写寄存器）；要换就重启
- 若确实需要 <100 kHz，只能改 `components/esp32-camera/Kconfig` 里的 `range`（本项目未做）

## 2. 灰度输出必须开 PSRAM DMA

OV2640 **没有真灰度模式**。esp32-camera 把 `PIXFORMAT_GRAYSCALE` 映射到 YUV422 寄存器组，
数据通路里 `in_bytes_per_pixel=2`、`fb_bytes_per_pixel=1`，靠 `cam_hal.c` 里这个分支压缩：

```c
if (psram_mode && in != fb) { /* 把 2B/px 压成 1B/px */ }
```

**`psram_mode` 为假时压缩不执行**，但 `fb_size` 仍按 `W*H*1` 计算 → 数据错位。

```c
CONFIG_CAMERA_PSRAM_DMA=y   // 必须
```

## 3. SDMMC 不能 DMA 读 PSRAM

S3 的 `SOC_SDMMC_PSRAM_DMA_CAPABLE` 未定义，`sdmmc_transaction.c` 遇到 PSRAM 缓冲直接返回
`ESP_ERR_INVALID_ARG`，且**没有 bounce buffer 兜底**。

后果：
- 录制缓冲在 PSRAM，**直接 `fwrite(psram_buf, ...)` 会失败**
- 必须经**内部 RAM 的 DMA 中转缓冲**（本项目 32 KB）逐块拷贝

```c
while (done < total) {
    memcpy(bounce, frames + done, chunk);   // PSRAM -> 内部
    fwrite(bounce, 1, chunk, f);            // 内部 -> SD
    done += chunk;
}
```

同理，FATFS 自己的缓冲也要留在内部 RAM：`CONFIG_FATFS_ALLOC_PREFER_EXTRAM=n`。

## 4. WiFi modem sleep 让每个请求慢 190 ms

默认 `WIFI_PS_MIN_MODEM` 会让下行包等下一个 DTIM 窗口。表现：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| ICMP RTT | **197 ms** | **31 ms** |
| `/api/status`（327 字节） | 190 ms | ~120 ms |
| 预览吞吐 | 5.3 req/s | 8.5 req/s |

```c
esp_wifi_set_ps(WIFI_PS_NONE);
```

> 判断技巧：**如果连几百字节的接口都要 100+ ms，先怀疑省电模式，而不是带宽。**

## 5. Nagle + 延迟 ACK：单请求固定多花 ~90 ms

关掉省电后，单请求仍 ~120 ms，且**与响应大小无关**。

原因：`esp_http_server` 的正常响应分两次 `write()`（头 + 体），而它**只对错误响应**
设置 `TCP_NODELAY`（`CONFIG_HTTPD_ERR_RESP_NO_DELAY`）。正常响应走 Nagle，等对端 ACK 才发第二段。

这个问题**从应用层关不掉**。对策是**并发**：

```js
const PV_WORKERS = 2;   // 页面开两个轮询通道，延迟不变、吞吐翻倍
```

实测预览从 8 fps 提到 **11~12 fps**。

## 6. `HTTPD_DEFAULT_CONFIG()` 的 `max_uri_handlers` 只有 8

路由加到 12 个后，**后 4 个静默不注册**（`httpd_register_uri_handler` 返回错误但没人检查）。

表现诡异：`/api/groups` 正常，`/api/stats` 直接 404 `Nothing matches the given URI`。

```c
cfg.max_uri_handlers = 16;   // 必须显式设置
```

## 7. `strtok` 吞空字段 → 索引整体错位

索引行格式 `name|label|v0|v1|v2|v3|frames|...`。若某字段为空（孤儿组的 `label` 就是空的）：

```
写入: data0099|0||0|0|0|0|R|0|500|0|2
strtok 读回: data0099,0,0,0,0,0,R,0,500,0,2   ← 少了一个字段，后面全部前移
```

结果 `frames` 和 `bytes` 互换，**元数据随机错位**，且不会报错。

**必须手工按 `|` 切分并保留空字段**：

```c
char *f[16]; int nf = 0;
f[nf++] = line;
for (char *q = line; *q; q++) {
    if (*q == '|') { *q = '\0'; if (nf < 16) f[nf++] = q + 1; }
}
```

## 8. 帧率会随光照变化（很容易被忽略）

OV2640 的自动曝光在**低照度下会拉长曝光时间**，直接拖低帧率。同一批实测数据：

| 类别 | 帧数 | 平均间隔 | 40ms 占比 | 判定 |
|---|---|---|---|---|
| fist | 12 | 40.0 ms | 11/11 | ✔ 干净 |
| circle | 12 | 40.0 ms | 11/11 | ✔ 干净 |
| victory | 75 | **55.5 ms** | 0/74 | ✘ 退化 |
| wave | 45 | **53.6 ms** | 0/44 | ✘ 退化 |
| wave | 75 | 41.1 ms (min=0, max=185) | 71/74 | ✘ 有异常帧 |

**后果**：如果切窗时按"40±4 ms"校验，这些片段**一条合格窗口都产不出来**。

**应对**：
1. 采集前看页面上的"预览 fps"，**接近 25 再开始**；明显偏低就补光
2. 训练侧必须按 `delta_ms` 过滤窗口，不能假设 40 ms
3. 若必须容忍变帧率，改为"按时间重采样到固定网格"，但要注意重采样本身会引入抖动

> 这也解释了为什么 `.gseq` 一定要存 `delta_ms`——不存就永远发现不了这件事。

## 9. 单泵分发，不要各自取帧

```c
// ✗ 错误：预览任务和录制任务各自 grab
preview_task: camera_driver_grab_gray(...)
record_task:  camera_driver_grab_gray(...)
```

`esp_camera_fb_get()` 是阻塞的队列取帧，两个任务抢同一个队列 → **双方都丢帧**，且丢帧时机不可预测。

正确做法是**一个泵任务取帧，再分发给消费者**：

```c
if (grab_gray(gray) == ESP_OK) {
    rec_pump_frame(gray);
    if (web_ui_preview_enabled()) web_ui_push_frame(gray);
}
```

## 10. 预卷不能吃掉整段

最初实现：预卷 = `min(15, 目标帧数)`。

对 12 帧的静态片段，预卷就把 12 帧全填满了 → **录的全是"按下之前"的画面**，而且还会多录 1 帧（`s_clip_n >= frames` 的判断只在 pump 里做，`rec_start` 里没做）。

修复两条：
- 预卷只取**片段长度的 1/4**（最多 15 帧），保证按下之后仍有 3/4 真实动作
- `rec_start` 结束后若已经录满，直接转 `WRITING`

## 11. 编号"不插补"必须持久化 next_id

只用 `next_id = max(现存编号) + 1` 是**不够的**：删掉最高编号的组后，`max` 回落，下次采集就会**复用**那个号。

正确做法：索引头部持久化 `# next_id=N`，删除触发重写时刷新它。

```
next_id = max(头部 next_id, 现存最大编号 + 1)
```

实测验证：删掉 `data0009`（当时的最高号）→ 重启 → `next_id` 仍为 10 → 新录得 `data0010`。

## 12. 页面在设备重启期间打开会永久卡死

```js
await loadConfig();   // 一旦失败，后面全部不执行
statusLoop();
previewWorker();
```

设备刚重启时 HTTP 还没起来，这一次 fetch 失败 → 整个页面变死（预览、状态、按钮全不工作）。

修复：**重试 + 失败提示**

```js
for (let i = 0; i < 20 && !CFG; i++) {
  try { await loadConfig(); } catch (e) { await sleep(500); }
}
```

## 13. 生成 JS/C 代码时的转义陷阱

用脚本生成代码时，`'\n'` 很容易被写成**真的换行**，导致：

- C 源码里格式化字符串断裂 → `error: missing terminating " character`
- JS 字符串断裂 → 整页白屏，且没有任何错误提示

```js
// ✗ 被写成真换行后语法错误
confirm('确认删除 3 组？\n' + names.join(','))

// ✓ 用 fromCharCode 绕开转义
confirm('确认删除 3 组？' + String.fromCharCode(10) + names.join(','))
```

**建议**：每次改完页面先跑一次语法检查

```bash
node --check <(sed -n '/<script>/,/<\/script>/p' index.html | sed '1d;$d')
```

## 14. 手机浏览器报 "Header fields are too long"（HTTP 431）

### 现象

- **电脑浏览器**一切正常
- **手机浏览器**打开页面只显示一行字：`Header fields are too long`
- 用 curl 加长 User-Agent 能稳定复现：

```bash
curl -A "Mozilla/5.0 ... $(python3 -c 'print("X"*600)')" http://<ip>/api/status
# HTTP 431  Header fields are too long
```

### 原因

ESP-IDF 的 httpd 把整个请求头收进一个编译期定长的 scratch 缓冲：

```c
// esp_httpd_priv.h
#define HTTPD_SCRATCH_BUF  MAX(HTTPD_MAX_REQ_HDR_LEN, HTTPD_MAX_URI_LEN)
```

而 `HTTPD_MAX_REQ_HDR_LEN` **默认只有 512 字节**。

桌面浏览器的请求头通常 300~500 B，勉强塞得下；手机浏览器的 User-Agent 本身就 120+ 字节，
再加上 `sec-ch-ua`、`Accept-Language`、cookie、`Priority` 等，**轻松破 1000 B**。

### 修复

```c
CONFIG_HTTPD_MAX_REQ_HDR_LEN=4096
CONFIG_HTTPD_MAX_URI_LEN=1024
```

代价几乎为零：scratch 缓冲在**每次请求**的 `httpd_req_aux` 里，不是常驻内存，加大只影响单次请求的瞬时占用。

### 实测

| 请求头大小 | 修复前 | 修复后 |
|---|---|---|
| ~400 B（桌面浏览器） | 200 | 200 |
| ~700 B（手机 UA） | **431** | 200 |
| ~2500 B（带一串 cookie） | **431** | 200 |
| ~5000 B（超过 4096） | 431 | 431（预期，够用了） |

> 判断技巧：**"桌面能用、手机不能用"** 且报错是 431/连接被关，基本就是这个缓冲太小。

## 15. 其它小坑

| 坑 | 说明 |
|---|---|
| `%u` 配 `uint32_t` | ESP32 上 `uint32_t` 是 `long unsigned int`，`-Werror=format` 会拦；显式 `(unsigned)` 转换 |
| `-Wformat-truncation` | `snprintf(path, 64, "%s/%s", dir253, name)` 会报错；用 `%.15s` 限定精度或放大缓冲 |
| `sdmmc_host_set_card_clk()` | 参数是 `int slot` 不是 card 指针；而且 IDF 已在协商时设好，不用自己调 |
| `get_reg()` 的 bank | OV2640 的 bank 编码在 **bit8**：读传感器 bank 的 PID 要传 `0x010A` 而不是 `0x0A`，否则读到 DSP bank 的 0 |
| 20 MS/s 采 20 MHz 时钟 | 会**混叠成一条直线**。看到"完全不动"的时钟先怀疑采样率，不是没信号 |
| 手机热点会休眠 | 无连接一段时间后自动关闭，表现为 `reason=201 NO_AP_FOUND`；测试时把热点设置页留在前台 |
| `mtime` 是开机计时 | 没有 RTC，跨重启的时间排序不可靠；需要真实时间就在 PC 侧用文件系统时间 |
