# 系统架构

## 1. 组件分层

```
                    ┌──────────────┐
   手机浏览器 ◄────► │   web_ui     │  HTTP 服务 + 内嵌单文件页面
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
 ┌─────────────┐   ┌──────────────┐   ┌──────────────┐
 │ cfg_store   │   │capture_record│   │  sd_index    │
 │ config.json │   │ 录制状态机   │   │directory.txt │
 └─────────────┘   └──────┬───────┘   └──────────────┘
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
      ┌──────────────┐        ┌────────────────┐
      │camera_driver │        │sd_files_driver │
      └──────────────┘        └────────────────┘
              │
      ┌──────────────┐
      │  esp32-camera│ (vendored)
      └──────────────┘
```

| 组件 | 职责 | 关键点 |
|---|---|---|
| `camera_driver` | 初始化 OV2640，统一输出 96×96 灰度 | 内部有降级链：XCLK 20→10 MHz、96×96→240×240 中心裁剪 |
| `sd_files_driver` | 挂载/卸载/剩余空间 | 只做挂载，不碰文件内容 |
| `cfg_store` | 解析 `config.json` + 校验 + CRC32 | 开机一次；失败回落内置默认 |
| `sd_index` | `directory.txt` 唯一读写入口 | RAM 索引 + 开机对账 |
| `capture_recorder` | 环形缓冲、录制状态机、`.gseq` 写入 | 落盘在 core1，经内部 DMA 中转 |
| `web_ui` | HTTP 服务 + 页面 | 12 个路由，注意 `max_uri_handlers` |
| `wifi_sta` | STA 连接 + 退避重连 | 关 modem sleep |

## 2. 启动顺序（`main.c`）

```
SD 挂载 ─► cfg_load ─► sd_index_init ─► camera_init ─► rec_init
                                                    │
                                        wifi_sta_start（失败也继续）
                                                    │
                                          web_ui_start
                                                    │
                                    创建取帧泵任务（core0）
                                                    │
                                              15 s 心跳日志
```

**顺序不能变**：
- `cfg_load` 必须在 `sd_index_init` 之前（索引头的 `cfg_crc` 取自配置）
- `rec_init` 必须在相机之后（要按 96×96 分配缓冲）
- WiFi 失败**不阻塞**——HTTP 服务照常起，只是外部访问不到

---

## 3. 取帧泵（核心数据通路）

```c
while (1) {
    if (camera_driver_grab_gray(gray, REC_FRAME_BYTES) == ESP_OK) {
        rec_pump_frame(gray);                    // ① 环形缓冲 + 录制追加
        if (web_ui_preview_enabled())
            web_ui_push_frame(gray);             // ② 预览（录制时关闭）
    }
}
```

**为什么是单泵而不是各自取帧**：

`camera_driver_grab_gray()` 内部是阻塞的 `esp_camera_fb_get()`。如果预览和录制各调用一次，两个任务会抢同一个 fb 队列，结果是**双方都丢帧**。单泵取一帧，再分发给两个消费者，时序才可控。

泵任务钉在 **core0**，优先级 **4**（低于 httpd 的 5，避免 HTTP 被饿死）。

## 4. 录制状态机

```
        rec_start(job)
IDLE ─────────────────► RECORDING ──(帧数满)──► WRITING ──(落盘成功)──► IDLE
  ▲                        │                      │
  │                        │                      └──(失败)──► ERROR
  └──────── discard ───────┘
```

- `rec_start` 先把环形缓冲里最近 `frames/4` 帧（最多 15 帧）作为**预卷**搬进录制缓冲，覆盖"按下按钮到真正开始录"的人为延迟
- `RECORDING` 期间每来一帧就追加；满了自动转 `WRITING`
- 写盘由独立任务（core1）完成，写完才把状态置回 `IDLE`

**缓冲占用**：环形 15 帧（135 KB）+ 录制 160 帧（1.44 MB），都在 PSRAM。

## 5. 存储结构

```
/sd/project/
├─ config.json         类别与变量定义
├─ directory.txt       唯一索引（一行一组）
├─ data0001/
│  └─ clip.gseq        一组 = 一次录制 = 一个文件
├─ data0002/
└─ ...
```

**选择"一组一目录一文件"的理由**：删除一组 = `unlink(clip.gseq)` + `rmdir(dataNNNN)` 两条调用，**不需要枚举目录内容**。若一组塞多个文件，删除就得先 readdir，成本和复杂度都上升。

索引与目录的对账策略：

| 索引有 / 目录有 | 处理 |
|---|---|
| ✔ / ✔ | 正常 |
| ✔ / ✘ | 启动时删掉该行（失效行） |
| ✘ / ✔ | 补录该组，标记 `ORPHAN`（不打开文件，只用 `stat` 拿大小） |

## 6. 任务与核分配

| 任务 | 核 | 优先级 | 说明 |
|---|---|---|---|
| 取帧泵 | core0 | 4 | 相机节奏驱动 |
| httpd | 默认 | 5 | HTTP 服务 |
| 落盘任务 | core1 | 4 | 写 `.gseq` + 更新索引 |
| 删除任务 | core1 | 3 | 逐组删除 + 重写索引 |
| WiFi | 系统 | — | 协议栈自有任务 |

**实测依据**：core1 被 45 ms/帧的忙等占满时，相机仍稳定 24.76 fps（因为取帧在 core0）；而把 SD 写放在 core0 会引发 120 ms 跳变。所以落盘一定要离开 core0。

---

## 7. 内存预算

| 项 | 大小 | 位置 |
|---|---|---|
| 相机帧缓冲 ×3 | ~85 KB | PSRAM |
| 环形缓冲 15 帧 | 135 KB | PSRAM |
| 录制缓冲 160 帧 | 1.44 MB | PSRAM |
| 索引表 8192 组 | ~384 KB | PSRAM |
| 配置结构 | ~2.7 KB | 静态区 |
| httpd 栈 | 8 KB | 内部 RAM |
| 预览帧缓冲 | 9 KB | 内部 RAM |
| 落盘中转缓冲 | 32 KB | 内部 RAM（DMA 能力） |

内部 RAM 余量约 **150 KB**（WiFi + httpd + 相机 + 录制器同时工作）。
